## A. Perimeter / API
| Item | Status | Notes |
|---|---|---|
| Rate limiting: strict on `/auth/*` (per-IP + per-account, exponential backoff, no hard lockout), moderate elsewhere; thresholds in config | ✅ | Every request: 120/min per IP. Login and signup: 10/min per IP. Login per username: 5 free attempts, then waits doubling from 1 s to 15 min, checked before the password and identical for unknown usernames; a correct password resets it. `429` with `Retry-After`. Bounded in-memory counters (ADR-12); `X-Forwarded-For` not trusted. Tests: `RateLimitTest`, `LoginThrottleTest`, `KeyedRateLimiterTest`. |
| Strict input validation (type, length, format); reject, never "clean" | 🟡 | Done for signup, login and incidents: format and length rules, unknown JSON fields rejected (including fields that belong to another incident kind), rejected values never echoed back. Incident text is kept exactly as sent and only ever returned as JSON data. IPs: plain four-number IPv4 or IPv6 only, parsed without any DNS lookup. To be repeated for every new endpoint. Tests: `IncidentApiTest`. |
| Security headers: CSP, `nosniff`, `X-Frame-Options: DENY`, HSTS | ✅ | Every response, including refusals: `Content-Security-Policy` (nothing may load or run), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, cross-origin opener/resource policies, `Cache-Control: no-store`; HSTS on HTTPS responses only (as the standard requires). No `Server` header. Tests: `ErrorHandlingAndHeadersTest`. |
| Request size limit | ✅ | Bodies over 256 KB refused with 413 before being read; chunked bodies without a length refused with 411; limit in config (`aBodyOverTheLimitIsRefusedBeforeItIsRead`). |
| HTTPS/TLS everywhere, including local demo | 🟡 | The gateway serves HTTPS only (port 8443), TLS 1.3 and 1.2 only; plain HTTP to the port is refused. Development certificate: self-signed, `localhost` only, marked not-a-CA, private key in a git-ignored, password-protected keystore. Trusting it is a separate, opt-in step for the current Windows user. Tests: `HttpsServerTest`. Production certificates come with deployment (step 17); agent-service traffic gets TLS when that service exists. |
| Live feed hardening: login required, ends with the session, limit on open connections | ✅ | Server-Sent Events (ADR-48, ADR-49). Needs a login; closes when the access token it opened with expires; 3 feeds per user and 200 in total; carries incident numbers only, announced after commit; a slow or vanished browser is dropped without holding anything up. Tests: `LiveFeedTest` (real HTTPS server), `LiveUpdatesTest`; part of the step's gateway mutation checks. |
| Demo routes cannot submit arbitrary content | ✅ | The browser only names a scenario; the gateway submits its own validated copy, marked `demo`, with ANALYST+ only; the routes disappear with `demo.enabled=false` (ADR-50). Tests: `DemoScenariosTest`, `DemoDisabledTest`, `DemoInvestigationTest`. |
| A red-team probe that shows the guardrails hold | ✅ | A scripted, hijacked model makes ten kinds of attempt through the real checks; the gateway judges each from what it stored and shows any that got through. Only the gateway's own route can ask the agent for the script (ADR-51). Tests: `RedTeamScorecardTest`, `RedTeamTest`, `InvestigationTest`, `agent/tests/test_redteam.py`. |
| The dashboard's own page policy | 🟡 | Strict CSP with no inline code, no framing, and requests to its own server only; `npm run dev` relaxes inline code for hot reloading. Checked by hand in a real browser under `npm run preview`. Tests: `dashboard/src/test/rules.test.ts`. Headers for production come with deployment. |
| Incident text is only ever text on the dashboard | ✅ | No HTML rendering, and no links from incident data. Markup placed in every field an attacker can influence stays as text and nothing runs. Evidence chips are made only from citations in the exact `E1` form. Tests: `dashboard/src/test/untrusted.test.tsx`, `rules.test.ts`; part of 25 dashboard mutation checks. |

## B. Authentication & authorization
| Item | Status | Notes |
|---|---|---|
| Passwords hashed with Argon2/bcrypt | ✅ | Argon2id, 19 MiB / 2 passes / 1 thread (OWASP minimum), settings in config. Random salt per password. Tests: stored value is an `$argon2id$` hash, same password gives different hashes, password never returned or logged (`AuthControllerTest`, `RequestRecordsTest`). |
| Login reveals nothing about which usernames exist | ✅ | Same message and same work for a wrong password and an unknown user (`wrongPasswordAndUnknownUserGetTheExactSameAnswer`). Signup does reveal a taken username; accepted, see ADR-21. |
| No self-assigned roles | ✅ | Every signup becomes `VIEWER`; a request containing `role` is rejected (`nobodyCanGiveThemselvesARoleAtSignup`). |
| Short-lived tokens + refresh rotation | ✅ | 15-minute signed access token (JWT, HS256 only). 7-day refresh token, random 256 bits, stored only as a SHA-256 fingerprint, single-use. Reusing an old one revokes the whole session. No grace period after expiry (the library's default is 60 seconds, ADR-49). Tests: altered, wrong-key, expired and unsigned tokens are all refused; rotation; reuse detection; logout (`SessionAndRolesTest`, `JwtServiceTest`). |
| HttpOnly + Secure + SameSite cookies | ✅ | Both cookies are `HttpOnly`, `Secure`, `SameSite=Strict`; the refresh cookie is limited to `Path=/api/auth`; tokens never appear in a response body (`loginSetsTwoLockedDownCookiesAndPutsNoTokenInTheBody`). |
| Cross-site request forgery (CSRF) protection | ✅ | State-changing requests from an unknown `Origin`, or marked `Sec-Fetch-Site: cross-site`, are refused; `SameSite=Strict` is a second layer (`requestsFromAnotherWebsiteAreRefused`). See ADR-25. |
| Role-based access (deny by default) | ✅ | Every URL needs a login unless explicitly listed as public; `/api/admin/**` needs `ADMIN`. Tests cover viewer, analyst and admin, self-promotion, and changing one's own role. |
| Object-level authorization on every endpoint | ✅ | Incidents are deliberately readable by every logged-in user (one team, ADR-38); submitting needs ANALYST or ADMIN. Deciding an action needs ANALYST or ADMIN, and nobody can decide one targeting their own account (ADR-47, `ActionServiceTest`). |

## D. Error handling & data protection
| Item | Status | Notes |
|---|---|---|
| Generic errors + trace ID to client; stack traces server-side only | ✅ | One error shape `{"error", "fields", "traceId"}` everywhere, including security refusals. Unexpected errors: generic message, full stack trace in the server log on a line tagged with the same trace ID. Framework errors keep their real status (404, 405, 400). Trace IDs are generated by the server, never taken from the caller. Tests: `ErrorHandlingAndHeadersTest`, including a check that a leaked message is caught. |
| Application uses a non-superuser database role | 🟡 | `scripts/setup-db.sql` creates `secanalyst_app` with no superuser, create-database or create-role rights. Checked by hand against a throwaway instance; no automated test. |
| Parameterised queries only | 🟡 | All queries so far use bound parameters. Database constraints reject malformed usernames (`AppUsersMigrationTest`). |
| Sensitive fields encrypted at rest | 🟡 | Employee baselines: AES-256-GCM in the gateway, key from `BASELINE_ENCRYPTION_KEY`, random nonce per write, identity bound as associated data, tampering detected (ADR-37). Evidence never copies baseline values, only differences from them (ADR-41). Tests: `BaselineCipherTest`, `MonitoredIdentitiesTest`, `agent/tests/test_baseline_check.py`. Incident payloads are not encrypted (they are what analysts read); revisit before real data. |
| Tamper-evident (hash-chained) audit log | ✅ | Each entry's HMAC-SHA256 covers the entry and the previous hash; the key is outside the database; `GET /api/audit/verify` reports the first break. A trigger refuses update, delete and truncate. The chain cannot show the newest entries being cut off, so the latest position also goes to the log file; comparing them is manual (ADR-46). Entries never hold incident text, tool arguments or a mistyped password. Tests: `AuditChainTest` (tampering with every field, missing entries, a forged key), `AuditEventsTest`, `InvestigationTest`; 14 mutation checks. |

## F. AI-specific hardening
| Item | Status | Notes |
|---|---|---|
| Incident text passed to the LLM as fenced data, never instructions | ✅ | The incident reaches the model as JSON inside `<untrusted_incident>` tags, with `<` and `>` escaped so the fence cannot be closed from inside; the system prompt says it is data and that instructions in it are evidence of an attack; the model sees tool summaries and findings, never raw results that could quote the attacker (ADR-44). Tests: `agent/tests/test_reasoning.py`. |
| Prompt-injection text detected and treated as evidence of an attack | ✅ | `pattern_match` finds injection phrasing after normalising the text (invisible characters, full-width and Cyrillic/Greek look-alike letters), and records it as `SIG-AI-INJECTION`; invisible characters are a finding of their own. The text is never followed. A red-team suite plays a model that obeys the injected note: its calls are refused and the verdict is never lowered. Tests: `agent/tests/test_patterns.py`, `agent/tests/test_reasoning.py`. |
| Fixed tool allow-list; arguments validated against the incident | ✅ | Every tool call passes one guardrail: unknown tools, and arguments that are not indicators extracted from this incident, are refused and recorded as `R1, R2, ...` (ADR-40). Since step 12 an AI model chooses the calls through the same guardrail; arguments must be named text values, and each tool takes a fixed set of argument names (ADR-44). Tests: `agent/tests/test_tools.py`, `agent/tests/test_reasoning.py`. |
| Every agent tool call logged | ✅ | Accepted and refused calls are both stored in the `evidence` table (label, tool, arguments, result or reason) and logged with the incident's trace ID. The gateway enforces the numbering and the database refuses repeated labels. Tests: `InvestigationTest`. |
| Data sent to the agent kept to what it needs | ✅ | Each request carries the incident, the subject's baseline, and other recent incidents' indicators as values and incident numbers only, never who those incidents were about (ADR-42); bounded to 1000 indicators. The AI model runs on the same machine and the agent refuses any other model address, so nothing goes to a third party; pseudonymisation would be needed only for a hosted model (ADR-15). |
| Agent service isolated and treated as untrusted | ✅ | Listens on `127.0.0.1` only; every request needs the service token (constant-time comparison); no database access and no state (ADR-3, ADR-4); API docs pages off; 1 MB body limit. The gateway re-validates every event it returns: known types and fields only, allow-listed statuses, size and time limits (ADR-5). Tests: `agent/tests`, `InvestigationTest`. |
| LLM output validated against a schema before use | ✅ | Every reply is size-capped (256 KB) and parsed defensively; tool calls go through the guardrail; `submit_verdict` must match a strict schema (unknown fields refused), cite existing evidence and come after evidence; refusal reasons never repeat the model's words, which never reach logs or the live stream; any failure hands over to the rule engine (ADR-44). Tests: `agent/tests/test_llm_client.py`, `agent/tests/test_reasoning.py`; 16 mutation checks. |
| Reports only repeat recorded evidence | ✅ | Both reports are built by code from the evidence chain; the gateway compares every finding and reason with the evidence it stored (evidence item, signal, words, weight, technique) and saves nothing if one differs. The plain report has no attacker text, no jargon, and reads at grade 8 or below (ADR-45). Tests: `agent/tests/test_report.py`, `InvestigationTest`. |
| High-risk actions need a human | ✅ | Proposals come from code, and the gateway's policy decides their risk and checks every target against what it stored. High-risk actions start pending and run only after an analyst or admin approves; a server-side role check, an atomic update (one decision wins, and it cannot be changed), expiry after 24 hours, and no deciding an action on your own account. Internal addresses and protected domains can never be blocked. Every step is in the audit log (ADR-47). Tests: `ActionServiceTest`, `InvestigationTest`, `agent/tests/test_actions.py`; 22 mutation checks. |
| AI-written text checked before anyone reads it | ✅ | One optional summary line, SOC report only: written from findings with every value masked, kept only if it is one short sentence citing existing evidence, with no address, link, number, copied incident text or reassuring claim; the gateway repeats the checks (ADR-45). Tests: `agent/tests/test_summary.py`, `InvestigationTest`; 12 mutation checks. |
| Limits on the AI model | ✅ | Per investigation: 8 turns, 120 seconds, 4 calls per turn. Per day: 200 AI-led investigations and 2 million tokens. Past any limit the rule engine finishes (ADR-15). Tests: `agent/tests/test_reasoning.py`, `agent/tests/test_budget.py`. |
| Detection measured on labelled incidents | 🟡 | 100 synthetic incidents modelled on published attack patterns: a 60-incident development set and a 40-incident held-out set written after the fixes the first set led to (ADR-53). Held-out, rule engine: 60% of attacks caught (target 90%, not met), 5% false alarms (target 10%, met). With the local AI model (one recorded run): 100% caught, 65% false alarms, because the model calls most findings "suspicious". Every result is in `docs/EVALUATION.md`, which CI checks against the agent on every pull request. Open: detection of calm requests with no tell-tale words, and calibrating the AI model's verdicts. Tests: `agent/tests/test_evaluation.py`; 6 mutation checks. |
| A verdict can never be lowered below the evidence | ✅ | The gateway recomputes the risk score from the evidence it stored and never lets the verdict fall below its band; claiming benign against the evidence is flagged as a disagreement and sent to a human; cited evidence must exist; the gateway, not the agent, sets the status (ADR-43). Since step 12 the standard checks always run after the AI model, so a model cannot shrink the evidence by skipping them (ADR-44). Tests: `InvestigationTest`, `RiskScoreTest`, the shared golden file. |
